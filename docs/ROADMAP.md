# קופת הסליק – תוכנית מעבר ופיתוח

> קובץ זה נשמר בריפו ב-`docs/ROADMAP.md`. Claude Code קורא אותו בתחילת כל שלב, מבצע **שלב אחד בלבד**, ומעדכן את סעיף "סטטוס" בסוף.

---

## 1. רקע

לפאב הקהילתי "הסליק" יש היום אפליקציית Google Apps Script Web App (קוד ב-`old_app_script_files/`, יועבר ל-`backend/legacy/`) שמנהלת:
- **רישום כרטיסיות** (`יומן מכירות`): רישום שמי של רכישת כרטיסיות לפי סוג (`סוגי כרטיסיות`: שם, מחיר, פעיל). החיוב בפועל נעשה מתקציב קהילתי חיצוני, והמערכת רק רושמת. **אין במערכת הקיימת יתרות** – רק רשומות רכישה.
- **אורחים:** אפשר לרשום רכישה גם למי שלא ברשימה, לפי שם חופשי (מפתח `guest|משפחה|פרטי`).
- **ביטול:** הבר יכול לבטל רישום עד 30 דקות; מנהל – כל עוד החודש פתוח. ביטול = שינוי סטטוס השורה (לא תנועה נגדית).
- **הוצאות** (`יומן הוצאות`) שמזין המנהל, כולל ביטול.
- **חוסרים** (`חוסרים`): רשימת טקסט חופשי עם סטטוס חסר/נקנה/נמחק.
- **תקופות חודשיות** (`תקופות`): טריגר יומי סוגר את החודש ביום האחרון ב-08:00, מפיק קובץ דוח (הכנסות/הוצאות/סיכום), נועל אותו, משתף לצפייה עם אנשי כספים ושולח מייל למנהל.
- **גיבוי שבועי** (טריגר ביום ראשון 04:00, שמירה 120 יום).
- **רשימת חברים:** נקראת מקובץ חיצוני לקריאה בלבד (Google Sheet או xlsx בדרייב), שם פרטי ושם משפחה בלבד. **מזהה החבר נגזר מהשם** – אין מזהה יציב.
- **הרשאות:** PIN בר ו-PIN מנהל **כתובים בקוד** (`Config.gs`), ובנוסף בעל הסקריפט לפי מייל. הגבלת ניסיונות שגויים דרך CacheService.

כל המידע נשמר ב-Google Sheets בדרייב.

**היעד:** אפליקציית ווב סטטית ב-GitHub Pages שרצה על טאבלט אנדרואיד מאחורי הבר, ומשמשת כקופה: לכל חבר יש ארנק שמי (יתרה בשקלים, לא כסף אמיתי), צ'יפ NFC שמזהה אותו, טעינה וחיוב לפי קטלוג מוצרים. **הטעינות** הן מה שמחויב בתקציב הקהילתי (מחליף את רישום הכרטיסיות).

## 2. החלטות ארכיטקטורה (סגורות)

| נושא | החלטה | נימוק |
|---|---|---|
| אחסון נתונים | נשאר ב-Google Sheets | שקיפות לצוות, חינם, ממשיכים את מה שקיים |
| Backend | Apps Script שפרוס כ-Web App ומשמש **JSON API בלבד** (בלי HTML) | Web NFC לא עובד בתוך ה-iframe של Apps Script |
| Frontend | React + Vite + TypeScript, PWA, פריסה ל-GitHub Pages דרך GitHub Actions | המפתח מכיר React; TS מונע באגים בחישובי כסף |
| ניהול קוד Apps Script | `clasp` בתיקיית `backend/` בתוך אותו ריפו | גרסאות, diff, ו-Claude Code יכול לערוך |
| מקור האמת ליתרה | **לדג'ר append-only** (גיליון תנועות). היתרה = סכום התנועות. עמודת `balanceCache` בגיליון החברים מתעדכנת בתוך הנעילה ומשמשת לקריאה מהירה; אפשר תמיד לחשב מחדש ולהשוות | אפשר תמיד לשחזר ולבקר; אין "עריכת יתרה" |
| זהות חבר | **גיליון `Members` בבעלות האפליקציה** עם `memberId` יציב (לא נגזר מהשם). הרשימה החיצונית נשארת **מקור החברות**, ומסונכרנת אל `Members` בתהליך סנכרון עם אישור מנהל | ארנק, תגים ודוחות חייבים מזהה שלא משתנה כשמישהו משנה שם או כשיש שני חברים עם אותו שם |
| זיהוי תג | התג מחזיק רק UID. מיפוי UID ← memberId בגיליון נפרד | אובדן צ'יפ = ניתוק תג ושיוך חדש, היתרה לא זזה |
| יתרת פתיחה | **כל החברים מתחילים ב-0.** רשומות הכרטיסיות הישנות נשמרות כארכיון לקריאה בלבד ולא מומרות ליתרה | במערכת הישנה אין יתרות, ואין מה להמיר |
| סכומים | מספרים שלמים באגורות בכל הקוד | אין שגיאות floating point |
| סודות | PINים, מייל מנהל ומזהי גיליונות נשמרים ב-**Script Properties**, PINים כ-hash. לא בקוד ולא בריפו | ה-API וה-frontend ציבוריים |

### מבנה הריפו
```
/frontend        React + Vite (PWA)
/backend         Apps Script (clasp), קבצי .gs/.ts
/backend/legacy  הקוד הישן (קריאה בלבד, לעיון)
/backend/core    לוגיקה טהורה (כסף, ביטולים, נרמול) – רצה גם ב-Node לבדיקות
/docs            ROADMAP.md, CURRENT_STATE.md, PARITY.md, DATA_MODEL.md, API.md, INVARIANTS.md
/.github/workflows/deploy.yml
CLAUDE.md        כללי עבודה לקלוד (ראה סעיף 8)
```

### מלכודות טכניות שחובה לטפל בהן
1. **CORS מול Apps Script:** לשלוח `POST` עם `Content-Type: text/plain` (גוף JSON כמחרוזת) כדי להימנע מ-preflight, ש-Apps Script לא תומך בו. לטפל גם ב-redirect ל-`script.googleusercontent.com`.
2. **מקביליות:** כל פעולת כתיבה עטופה ב-`LockService.getScriptLock()`. בתוך הנעילה: בדיקת idempotency ← בדיקת יתרה ← כתיבת תנועה ← עדכון cache.
3. **Idempotency:** כל פעולה מהלקוח נושאת `clientTxId` (UUID). השרת מתעלם מכפילויות ומחזיר את התוצאה המקורית. זה קריטי כי בלי זה ניסיון חוזר ברשת חלשה = חיוב כפול.
   - **ביצועים:** הקוד הישן מחפש מזהה בסריקה לינארית של כל הגיליון (`findRowById_`). על לדג'ר שגדל כל ערב זה לא יחזיק. יש לבדוק קודם ב-CacheService (מפתח `tx:<clientTxId>`, תוקף 6 שעות) ורק אחר כך בסריקה של N השורות האחרונות בלבד (לקוח לא שולח ניסיון חוזר אחרי יותר מכמה שעות; תור אופליין בשלב 8 מגביל את הגיל).
4. **אבטחה:** ה-Web App פרוס עם `access: ANYONE` ו-`executeAs: USER_DEPLOYING`, וה-URL של ה-API גלוי בקוד ב-GitHub Pages. לכן:
   - **Device token**: נוצר במסך הגדרת מכשיר (ע"י מנהל), נשמר ב-localStorage, ומאומת בשרת מול גיליון `Devices` (hash). אפשר לבטל מכשיר.
   - **PIN משמרת** לברמן (פתיחת משמרת), **PIN מנהל** לפעולות מנהל. hash ב-Script Properties, הגבלת ניסיונות שגויים לכל מכשיר.
   - **PINים הנוכחיים נחשבים חשופים** (הם כתובים בקוד). מחליפים אותם בעלייה לאוויר של שלב 1.
   - הגיליונות עצמם: עריכה רק לבעלים ולסקריפט. לא נדרשת אבטחה ברמה בנקאית, אבל כן הגנה מפני "מישהו מצא את ה-URL".
5. **מהירות:** Apps Script עונה בערך תוך 1–3 שניות. ה-UI חייב להיות אופטימי עם אינדיקציה ברורה (ממתין / אושר / נכשל), ולא לחסום את הברמן. יתרה מוצגת מ-`balanceCache`, לא מחישוב כל הלדג'ר.
6. **בדיקות:** הלוגיקה הכספית נכתבת כפונקציות טהורות ב-`backend/core` (בלי `SpreadsheetApp`), כדי שאפשר יהיה להריץ אותה ב-Node ב-CI. שכבת ה-Sheets והנעילה נבדקת בבדיקות אינטגרציה מול staging.

## 4. כללים עסקיים של הקופה (מחייבים)

1. **טעינה:** מותרת לכל איש צוות במשמרת פתוחה. אין הרשאת מנהל ייחודית. כל טעינה נרשמת עם shiftId ושם/ות הצוות.
2. **אין יתרה שלילית.** חיוב שיוריד את היתרה מתחת ל-0 **נחסם בשרת** (לא רק ב-UI).
   - כשהחיוב חוסם, או כשהיתרה מגיעה ל-0, נפתח דיאלוג: "אין מספיק יתרה, לטעון?". אישורו מבצע **טעינה + חיוב כפעולה אטומית אחת** בשרת (שתי תנועות באותה נעילה, עם אותו clientTxId בסיס), כך שאי אפשר להשאיר את הטעינה בלי החיוב או להפך.
   - יתרה 0 לאחר חיוב היא מותרת. הדיאלוג מוצג כהתראה בסריקה הבאה.
3. **ביטול עסקה אחרונה (ע"י הצוות):** מותר רק אם
   - עברו פחות מ-30 דקות מהעסקה, **וגם**
   - לא בוצעה שום פעולה נוספת **על החשבון של אותו חבר** מאז.
   - ביטול = תנועת REVERSAL חדשה שמפנה ל-txId המקורי. לא מוחקים שורות. גם המלאי מוחזר (משלב 7).
   - ביטול של טעינה+חיוב אטומי מבטל את שתיהן יחד.
   - אי אפשר לבטל תנועה פעמיים, ואי אפשר לבטל REVERSAL.
4. **ביטול מאוחר / חריג:** רק מנהל (PIN מנהל), עם שדה סיבה חובה. נרשם ב-Audit. ביטול שהיה מוריד את היתרה מתחת ל-0 (למשל ביטול טעינה שכבר נוצלה) נחסם, והמנהל משתמש ב-ADJUSTMENT עם סיבה.
5. **אובדן צ'יפ:** מנהל או צוות מסמנים את התג כ-`lost`, ומשייכים תג חדש לאותו memberId. היתרה וההיסטוריה לא משתנות. סריקה של תג `lost` מציגה אזהרה ולא מאפשרת חיוב.
6. **חיוב בלי צ'יפ:** אפשרי מתוך חיפוש שמי, בתנאי שמסומן "שכחתי צ'יפ" (`noChip` בתנועה). עד שלב 6 (NFC) כל החיובים הם מחיפוש שמי.
7. **מלאי (משלב 7):** כל חיוב של מוצר עם `trackStock` מייצר אוטומטית StockMovement מסוג SALE, וביטול מייצר REVERSAL.
8. **אורחים:** אורח (מי שלא ברשימה החיצונית) נוצר ב-`Members` עם `source=GUEST`, ומקבל ארנק כמו כל חבר. הדוח החודשי מציג אורחים בנפרד.
9. **תקופות:** כל תנועה ושורת הוצאה משויכת לחודש לפי זמן הרישום. "משמרת" שנמשכת אחרי חצות שייכת לתאריך של הערב (עד 08:00 בבוקר, כמו היום). סגירת חודש לא חוסמת חיובים, אבל ביטול צוות של תנועה מחודש סגור אסור (רק מנהל, עם ADJUSTMENT).

## 5. השלבים

כל שלב מסתיים במצב שעובד בפרודקשן. לא מתחילים שלב לפני שהקודם עבר את קריטריוני הקבלה.

**סדר השלבים ונימוק:** קודם זהות (חברים) ותשתית, אחר כך הקטלוג שהקופה צריכה, אחר כך הארנק, ורק אחריו NFC ומלאי מלא. ניהול מלאי מבוסס תנועות הוא השלב הגדול ביותר והפחות קריטי למטרה המרכזית, ולכן הוא מגיע אחרי שהקופה עובדת. רשימת החוסרים הקיימת ממשיכה לעבוד כמו שהיא עד אז.

### שלב −1 – העברה לחשבון Google ייעודי
- האפליקציה הקיימת (קוד + כל הגיליונות + הדוחות החודשיים) מועתקת מהחשבון הפרטי לחשבון Gmail ייעודי לפאב. **שום נתון בחשבון הפרטי לא משתנה**: החשבון הייעודי מקבל למקור הרשאת צפייה בלבד, וההעתקה נעשית ב"יצירת עותק" + הסקריפט `migration/Migrate.gs`.
- הסקריפט מנקה Script Properties שהועתקו (`MASTER_ID` וכו', שאחרת מצביעים על המקור), מעתיק את הדוחות לתיקייה חדשה ומעדכן את הקישורים ב-`תקופות`, יוצר טריגרים, ומאמת כל גיליון מול המקור (מספר שורות + hash).
- רשימת החברים החיצונית משותפת ע"י בעליה עם החשבון הייעודי (צפייה). תנאי למעבר.
- באפליקציה הישנה נמחקים רק שני הטריגרים (מניעת דוח כפול). הנתונים והקוד נשארים.
- מכאן: staging, clasp ופרודקשן – כולם בחשבון הייעודי. GitHub נשאר בחשבון האישי.
- הוראות מלאות: `migration/MIGRATION.md`.
- **קבלה:** הרצת ניסיון ירוקה, הרצה אמיתית ירוקה, רישום ניסיון בכתובת החדשה נכתב לעותק בלבד, והבר עובד בכתובת החדשה.

### שלב 0 – מיפוי, חוזים וסביבת staging
- לייבא את קוד ה-Apps Script הקיים עם `clasp pull` לתיקיית `backend/legacy/`.
- לכתוב `docs/CURRENT_STATE.md`: כל הפונקציות, כל הגיליונות והעמודות, כל המסכים והזרימות, כל הטריגרים (סגירה יומית, גיבוי שבועי) והמיילים.
- לכתוב `docs/PARITY.md`: טבלה של **כל יכולת קיימת** ← באיזה שלב היא נשמרת, משתנה או מוחלפת, ולמה. אף יכולת לא נעלמת בשקט.
- לכתוב `docs/DATA_MODEL.md` (סכמה סופית לכל הגיליונות, סוגי תנועות, כללי idempotency וביטול) ו-`docs/API.md` (כל ה-actions, קלט, פלט, שגיאות, הרשאה נדרשת).
- לכתוב `docs/INVARIANTS.md`: רשימת אינווריאנטים כספיים, כל אחד ממופה לבדיקה אוטומטית (ראה שלב 5).
- ליצור **עותק staging** של הספרדשיט ופריסת Apps Script נפרדת ל-staging. כל הפיתוח נעשה מול staging. הרשימה החיצונית ב-staging היא עותק עם שמות פיקטיביים.
- **קבלה:** חמשת המסמכים מאושרים ע"י המשתמש, ו-staging עובד.

### שלב 1 – מעבר 1:1 ל-GitHub Pages (בלי פיצ'רים חדשים)
- Backend: router אחד ב-`doPost` (`{action, payload, auth, clientTxId}`) ← handlers. תגובה אחידה `{ok, data | error: {code, message}}`.
- Frontend: שחזור כל המסכים הקיימים (רישום כרטיסיות כולל אורחים, ביטול, הוצאות, חוסרים, מצב משמרת) ב-React. RTL מלא, עברית, כפתורים גדולים לטאבלט (מינימום 48px), מצב landscape.
- **תקופות ודוחות:** סגירת חודש אוטומטית, הפקת קובץ הדוח, נעילה, שיתוף עם אנשי כספים ומייל חודשי ממשיכים לעבוד בדיוק כמו היום (הטריגרים נשארים בצד השרת).
- **גיבוי שבועי** ממשיך לעבוד.
- PWA: manifest, service worker לקבצים סטטיים, אייקון, אפשרות "הוסף למסך הבית".
- **אבטחה:** העברת PINים, מייל מנהל ו-URL הרשימה החיצונית מ-`Config.gs` ל-Script Properties (PINים כ-hash). Device token + PIN משמרת (התשתית, גם אם בשלב זה רק כניסה פשוטה). **החלפת ה-PINים הנוכחיים** ביום העלייה.
- GitHub Actions: build + deploy ל-Pages; ה-API URL כ-env variable בזמן build. בדיקות `backend/core` רצות ב-CI.
- **קבלה:** כל שורה ב-`PARITY.md` שמסומנת "שלב 1" עובדת בחדשה, מול אותם גיליונות, על כרום באנדרואיד. דוח חודשי אחד הופק מהמערכת החדשה וזהה לדוח מהישנה. האפליקציה הישנה נשארת זמינה כגיבוי.

### שלב 2 – חברים וזהות
- גיליון `Members` בבעלות האפליקציה, עם `memberId` יציב.
- **סנכרון מהרשימה החיצונית** (פעולת מנהל, לא אוטומטית): המערכת מציגה diff – חברים חדשים, חברים שנעלמו מהרשימה (→ inactive, לא נמחקים), שינויי שם אפשריים (התאמה לפי externalKey), ושמות כפולים. המנהל מאשר שורה-שורה או הכל.
- **שמות כפולים:** שני חברים עם אותו שם מקבלים `displayName` מובחן (למשל תוספת אות/טלפון), שהמנהל קובע.
- **אורחים:** אורח נוצר ב-`Members` עם `source=GUEST`. מנהל יכול למזג אורח לחבר מהרשימה (מיפוי, לא מחיקה).
- **LegacyKeyMap:** מיפוי כל מפתח שם ישן (כולל אורחים מ-`יומן מכירות`) ל-memberId, כדי שהארכיון וההיסטוריה יהיו ניתנים לקישור.
- רישום הכרטיסיות (משלב 1) עובר לעבוד מול memberId במקום מפתח השם.
- מסך מנהל: רשימת חברים, חיפוש, עריכת displayName/טלפון/סטטוס.
- **קבלה:** סנכרון מלא אחד בוצע ואושר, כל המפתחות מ-`יומן מכירות` ממופים, ואין שני חברים פעילים עם אותו displayName.

### שלב 3 – זיכויים בהוצאות
- שדה `type` (הוצאה/זיכוי) בטופס ההוצאות. זיכוי נשמר כסכום חיובי עם type=CREDIT, והסיכומים מחשבים נטו.
- הצגת נטו בדוחות הקיימים. מיגרציה: כל השורות הישנות מקבלות type=EXPENSE.
- **קבלה:** הדוח החודשי מציג הוצאות, זיכויים ונטו בנפרד.

### שלב 4 – קטלוג מוצרים
- `Products`: ניהול מוצרים, קטגוריות ומחירים (CRUD) במסך מנהל. **זה הקטלוג שהקופה תשתמש בו בשלב 5.**
- מוצר "פריט חופשי" (`isOpenPrice`) שבו הברמן מזין סכום.
- `trackStock` ו-`minLevel` כבר קיימים בסכמה, אבל עדיין לא בשימוש (שלב 7).
- מחיקה = `active=false`. מוצר שהופיע בתנועה לא נמחק.
- **קבלה:** הקטלוג המלא של הבר מוזן ומאושר ע"י המשתמש.

### שלב 5 – ארנק וקופה (בלי NFC עדיין)
- `Transactions`, מסך קופה: חיפוש חבר לפי שם ← כרטיס חבר (שם, יתרה, 5 תנועות אחרונות) ← גריד מוצרים לפי קטגוריות ← סל ← חיוב.
- טעינה בסכומים מוגדרים מראש (50/100/200) + סכום חופשי.
- כל כללי סעיף 4 (חסימת שלילי, טעינה+חיוב אטומי, ביטול 30 דקות, ביטול מנהל, אורחים, תקופות).
- `balanceCache` מתעדכן בתוך הנעילה. פעולת מנהל "בדיקת עקביות" מחשבת מחדש מהלדג'ר ומסמנת פערים.
- **מעבר (cutover):**
  - כל החברים מתחילים ביתרה 0. אין תנועות פתיחה.
  - תאריך מעבר מוגדר מראש = תחילת חודש. מאותו תאריך הקופה מחליפה את רישום הכרטיסיות; `יומן מכירות` הופך לארכיון לקריאה בלבד.
  - **ריצה במקביל:** בערב הפיילוט הראשון הצוות רושם גם בדף נייר/בישנה, ובסוף הערב משווים.
- **דוח חודשי לגבייה** (מחליף את דוח ההכנסות מכרטיסיות): **סך הטעינות** לכל חבר (זה מה שמחויב בתקציב הקהילתי), לצד צריכה ויתרת סוף חודש. אורחים בנפרד. ממשיך להיווצר, להינעל ולהישלח במייל כמו היום.
- **בדיקות:**
  - **יחידה (Node, ב-CI):** לכל הלוגיקה ב-`backend/core`, לכל אינווריאנט ב-`INVARIANTS.md`, כולל לפחות:
    - יתרה = סכום התנועות, אחרי כל רצף פעולות.
    - אין חיוב שמוריד מתחת ל-0; טעינה+חיוב הם הכל-או-כלום.
    - שליחה חוזרת של אותו clientTxId = אין שינוי, ומוחזרת התוצאה המקורית.
    - ביטול נחסם אחרי 30 דקות, אחרי פעולה נוספת על אותו חבר, ופעם שנייה.
    - ביטול מנהל שהיה מוריד מתחת ל-0 נחסם.
    - סכום הטעינות בדוח = סכום תנועות TOPUP פחות ביטולי TOPUP בחודש.
    - שיוך לחודש/משמרת סביב חצות, 08:00 וסוף חודש.
  - **אינטגרציה (מול staging):** סקריפט ששולח 20 חיובים מקבילים לאותו חבר עם יתרה ל-10 מהם ומוודא שבדיוק 10 עברו; ושליחה כפולה של אותו clientTxId.
- **קבלה:** כל הבדיקות ירוקות, וערב פיילוט אחד עם חיפוש שמי בלבד, בלי פערים בין הדוח לספירה הידנית.

### שלב 6 – NFC
- שכבת הפשטה `TagReader` עם שני מימושים:
  - `WebNfcReader` – `NDEFReader.scan()`, קריאת `serialNumber`.
  - `KeyboardWedgeReader` – קורא USB שמקליד UID + Enter (שדה מוסתר עם פוקוס קבוע, זיהוי לפי מהירות הקלדה).
  - נרמול UID: hex, אותיות גדולות, בלי מפרידים, וכן טיפול בסדר בייטים הפוך. בדיקות יחידה לנרמול עם דוגמאות משני סוגי הקוראים.
- סריקה ← פתיחת כרטיס חבר מיידית.
- מסך הנפקה: סריקת תג חדש ← בחירת חבר מרשימה ← שיוך. תג שכבר משויך לחבר אחר נחסם.
- זרימת "צ'יפ אבד": בחירת חבר ← סימון התג הישן כ-lost ← סריקת תג חדש.
- סריקה של תג לא משויך מציעה "לשייך לחבר?".
- **קבלה:** 20 סריקות ברצף בלי החמצות **בכל אחד מסוגי הקוראים שבשימוש**, ושיוך מחדש של צ'יפ שאבד עובד מקצה לקצה.

### שלב 7 – ניהול מלאי מלא
- מלאי מבוסס תנועות: קבלת סחורה, ספירת מלאי (מזינים כמות בפועל, המערכת רושמת את ההפרש), פחת.
- חיוב בקופה של מוצר עם `trackStock` יוצר SALE, וביטול יוצר REVERSAL (כלל 7).
- "חוסרים" הופך לתצוגה מחושבת: מוצרים שמתחת ל-minLevel, ורשימת קניות מוכנה לשיתוף בוואטסאפ. פריטי טקסט חופשי עדיין אפשריים לדברים שלא בקטלוג.
- מיגרציה של רשימת החוסרים הקיימת: פריטים פתוחים שתואמים מוצר ← ממופים; השאר נשארים כטקסט חופשי.
- **קבלה:** ספירת מלאי מלאה אחת בוצעה במערכת, והתצוגה תואמת למציאות.

### שלב 8 – הקשחה
- תור אופליין: פעולות נשמרות ב-IndexedDB עם clientTxId ונשלחות כשחוזרת רשת. **באופליין מאפשרים חיוב רק עד היתרה האחרונה הידועה במטמון**, וטעינות בלבד מעבר לזה. התנגשויות מסומנות למנהל. פעולה בתור ישנה מ-6 שעות דורשת אישור מנהל לפני שליחה. בדיקת יחידה: התור לעולם לא מאשר חיוב מעבר ליתרה במטמון פחות חיובים שכבר בתור.
- סגירת משמרת: סיכום טעינות/חיובים/ביטולים במשמרת.
- גיבוי **יומי** אוטומטי של הספרדשיט (שדרוג מהשבועי הקיים; time-driven trigger שמעתיק לתיקיית גיבויים), כולל ניקוי גיבויים ישנים.
- מצב קיוסק לטאבלט (מסך מלא, מניעת יציאה בטעות), מצב כהה לבר חשוך.

## 8. כללים ל-CLAUDE.md

- שלב אחד בכל פעם. אסור לממש פיצ'רים משלבים עתידיים.
- לעולם לא לכתוב לספרדשיט הפרודקשן בזמן פיתוח. רק staging.
- לעולם לא למחוק או לערוך שורות ב-`Transactions`. רק להוסיף.
- כל כלל עסקי נאכף **בשרת**. ה-UI רק משקף.
- סכומים באגורות (integer). אסור float בחישובי כסף.
- כל פעולת כתיבה: LockService + clientTxId + רישום ב-Audit.
- לוגיקה כספית רק ב-`backend/core` כפונקציות טהורות. כל כלל או אינווריאנט חדש מגיע עם בדיקה.
- אסור לשמור PINים, טוקנים, מיילים או מזהי גיליונות בקוד או בריפו. רק ב-Script Properties / משתני build.
- מזהה חבר הוא תמיד `memberId`. לעולם לא לגזור זהות משם.
- UI: עברית, RTL, גוף זכר בטקסטים (או ניסוח ניטרלי), כפתורים גדולים, פידבק ברור להצלחה/כישלון.
- לפני שינוי סכמה: להציג diff של הגיליונות ולקבל אישור.
- אף יכולת קיימת לא מוסרת בלי שורה מתאימה ב-`PARITY.md`.
- בדוגמאות ובנתוני בדיקה להשתמש בשמות פיקטיביים בלבד (ישראל ישראלי וכו'), לא בשמות חברים אמיתיים.
